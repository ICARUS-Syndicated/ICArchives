崩坏

Dies irae, dies illa! Vos solvet in favilla. Maledictus erus in flammas aeternas!
神怒之日，世界毁日！将一切焚为灰烬；被诅咒之人，永堕烈火之中！

七天。上帝创世用了七日，而直到这一切化为虚空中的一连串的无意义高熵数据流（推测，存疑），也只花了七日。
三月三日木白宣布热更新，开始把插件体系从 SunLight 迁出去；三月四日凌晨问题接踵而至：homes 无法迁移，tpa 和 rtp 丢失，地标被迫改为改 /pw；三月四日到五日附魔插件出现物品重叠 bug；三月六日到八日主城持续掉帧、TPS 掉到 10、整批掉线；三月八日凌晨测试账号在经过检查之后判定“主城炸了”“并且是因为粒子效果”，且“不能”区块级回档。
三月九日二十三点二十四分，Laugh_TheLiving 掉线重上，背包空了；但是在线的三个人中，一个管理也没有。

二十二点五十五分，anioto 说“被禁人塔搞了”。无法确定服务器里已经出现了人为的区块禁用装置还是这只是一句玩笑话，但是可以确定的是，当时服务器极其卡顿。

十八点十五分，anioto 说“主城这个bug就是得修”，因为很明显如果这个严重的问题如果不解决则会影响到所有玩家。十八点十六分她又说：“以前进服还会重制模式”“唉唉sunlight”。

直到彼时，根本没人会知道第二天会发生什么。

kenny 回他五个字：

“服务器文件没了”

“卧槽，玩呢；一点备份存档都没有吗” “天塌了woc，我才是被雷击的那个”

十七点三十五分，乐凝发布了《五周目最后一条公告》：

“因为不可抗力，我们可能要说再见了。（rwp 5周目，——2026.3.9） 由于攻击和 mcsm 自身漏洞，服务器所有文件被异常删除。我们发现时已在深夜，最近的备份处在2025年12月，玩家数据保存在3月4日……”

落款是“红白阁管理组，猫anioto　2026年3月10日凌晨”。

那么，实际上……？​

ICAI 文档对这件事记录只有一行：

“由于意外格式化工作目录删档之后，管理组发现先前的备份至少是一个月前的，由此而定，不予重开。” ———— Ph0sphorW

紧接着是另一行，来自乐凝：

我当时就炸了。
真实原因并非没有备份而是升1.21.11的时候删了。。
———— neko_annieawa

sam 本人对这件事件的看法是：

你和乐凝两个整的那一套东西，放在mcsm上是存在一个反序列化漏洞链的，而好巧不巧mcsmapi和daemon都没有验证这个东西
应该是木白你传了个空文件上去被反序列化成.了

然而经过笔者仔细的查询，并阅读相关源代码之后，并没有任何与上传空文件后将会格式化工作目录相关的任何 issue tracker 得到汇报。
进一步的审计发现，仓库全 commit 记录中没有任何其所谓的“反序列化漏洞链”进行修复；如果真的如其所言，那么笔者抛出如下几个问题：

  • 首先，假设其所说格式化工作目录这一信息为真，那么在其工作目录被格式化时为什么服务端仍旧在保持运行甚至能够在断开连接之后继续进行正常运行，甚至没有爆出任何一条相关的 JVM 虚拟机内存转储？甚至于，velocity 的日志记录完整记录了每个玩家每一句话，也就是说插件文件夹是完好无损的（若此时才加载 db driver 那么必定 no class def 而被禁用），那么为什么这些文件没被损坏？
  • 其次，假设真的只是三个世界正好被波及到，那么按照道理来说会触发 MC 的保护机制，也即世界重新生成，没有问题吧？但是首先，world 作为主世界不能被卸载的，其次，假设 world.dat 被冲得一塌糊涂，那么将残余的 region 进行重建，这也并不困难吧？难道真的非常偶然的有一股数据流正好把 logs 和 worlds 全部冲成了一篇断壁残垣？
  • 第三，退一万步假设，即使真的上述成立，那么本地 mysql 被下线是什么操作？，即使使用了插件列表中最有可能暴露漏洞的 rcon （是的，在回收数据中找到了他们启用 rcon 的配置甚至为此写了一个插件），那么这种行为到底如何解释？
  • 最后，假设真的按照 JVM 的机制按需加载 class，那么在崩溃时即使因为 NoClassDef 或者是直接整个抛出 jvm dump 吧；然而上述两种可能潜在的记录全部不存在于回收数据中。

延时 qwq 给出了一种解释，当服务端工作目录整个被格式化时，那么整个服务端将只运行于 jvm 中而无法进行任何 I/O。彼时一旦牵扯到 I/O，那么就会出现大量报错。也即，这是一个“幽灵服务器”。但是很明显，在原本的情景中 I/O 甚至可以说没有特别大的影响，所以这种说法不成立，或者部分成立。

即使按照所给出的“上传.文件导致删除时删除整个工作目录”的说法，那么难道管理层没有任何一个人去怀疑这段话本身的正确性与否吗？

const blackList = ["\\", "/", ".."];
    for (const ch of blackList) {
      if (name.includes(ch)) return false;
    }

各位请看 system_storage.ts 中的L10 - L13，很明显，黑名单中是不存在 "." 这一项的，那么能说明是上传了一个空文件被序列化为点，或者是人为上传了一个点文件然后删除导致的吗？
各位要知道的是现代操作系统根本没有那么傻， 文件系统针对 . 文件是有防范措施的。 上传一个点文件在 upload 的时候会抛出一个 hard io error，或者说将之进行重命名也会如此。即使是在极端情况下，通过修改上传请求令其命名为一个点，那么文件系统同样会抛出 i/o error。
综上，“因为反序列化漏洞”命名为 . 随后删除 . 文件导致整个文件夹被删除这种说法，是根本站不住脚的。
那么到底是什么人，或者什么事导致的这一切呢？

经过笔者推测，这件事最有可能的原因，极有可能是某位管理员操作不慎，或者是有意为之操作的。
这位管理员有极高的权限，能够把 mysql 的服务停止，能够将 world 整个删除，并且能够在事发之后紧急停止甚至直接杀死服务端进程。那一天可能出于想要更新的目的，或者是出于其它任何想法，将 sql 断开（或者是在配置文件中修改了）并将 world 删除，但在发现这并不是测试用服务器并且自己已经酿成大祸之后选择了紧急关停服务器并装作不知道。
但是我们目前手头没有任何有关材料能够证明上述这一切是否正确。

不论如何，我们没有证据，只能推测。

后天​

公告给了三条方案：搬迁、迁址（新地图先开，自由选址）、转存（物品暂存，以完成进度的形式获取）。
苏哥的回应基本代表了所有玩家共同的想法：

“我那么大个的综合性基地，还有那些物资，包括周边建筑，这是一个完整的工业链，能养活半个服务器的玩家那种，不是说帮忙就能解决的，那全是真金白银的电费和时间堆积出来的”

samuioto 的回应也很直接：“到现在没查出来确切原因　也没有人做错事　丢的莫名其妙的”。他还补了一个技术细节：

“从用户第一次登陆到数据被删除导致的第一条报错的时间段　一点日志没有”
“网络审计是外挂的　也没查出任何问题”

但是这一条关键的报错去哪里了呢？
还有一处更无法理解的矛盾。3 月 9 日不是存档丢失，是玩家数据丢失……地图本身完好。这一点由当事人 Laugh_TheLiving 在二十三点四十一分亲口确认：『现在是人的存档全没了』『地图没事』。
群里没有任何一条能裁决这一点。三月九日二十三点的群聊只有四个撤回标记和三条系统消息，一片空白；三月十日上午八点五十三分，管理“群猫猫(≥v≤)”说的是“难受的是搓了那么久的村交没了……”。
十八点十三分，samuioto 说了一句“对不起大家喵......”。这是他在这件事里唯一一次道歉。
没有任何管理方在游戏里解释过这件事，也不可能解释。所有相关的沟通都发生在群里，甚至，最关键的，管理群。但是我们无从知晓管理群里到底发生了什么。

六朝旧事随流水，但寒烟衰草凝绿。
